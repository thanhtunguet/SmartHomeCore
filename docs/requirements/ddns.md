## DDNS

| ID | Requirement | Status | Verified by |
|----|-------------|--------|-------------|
| REQ-DDNS-001 | **Public-IP discovery with quorum.** The address is asked from `controller.ddns.ip_providers` (at least 2, on different hosts, `https` only). It is accepted only if **at least 2 providers return the same address and no other address has as many answers**; one source is never enough, a tie fails. The answer must be a bare address of the requested family (`A` = IPv4, `AAAA` = IPv6) and **public**: loopback, private, link-local, CGNAT, documentation, multicast, 6to4, NAT64, Teredo and other non-global ranges are rejected. Requests are pinned to the family at the socket, bounded (5 s, 128-byte body), use no proxy, and follow at most 3 redirects **on the same host**. Concurrent callers share one in-flight discovery and a success is cached for 10 s per family (failures are not cached), so many configurations cost one round of requests. A provider URL may carry a key, so only the **host** is ever logged or returned. Failure is transient (the syncer backs off). | Implemented | `TestQuorumDecision`, `TestFamilyAndRangeChecks`, `TestDiscovererAgreementAndValidation`, `TestDiscovererCachesAndSharesInflightRequests`, `TestDiscovererDoesNotCacheFailures`, `TestDiscovererCancelledCallerDoesNotPoisonOthers`, `TestDiscovererTimesOutSlowProviders`, `TestNewDiscovererValidatesProviders`, `TestDiscovererOverRealHTTP` |
| REQ-DDNS-002 | **Cloudflare client** (stdlib `net/http`, no SDK, Cloudflare API v4): list zones and `A`/`AAAA` records (paginated, ordered by name), read one record by id, `PATCH` only `content`, `proxied` and `ttl` (name and type are never sent). The token is sent only as `Authorization: Bearer`. Responses are decoded from the `{success, errors, result, result_info}` envelope with a 4 MiB cap; redirects are not followed; ids are validated before they become URL path segments. Failures are `CloudflareError`s carrying Cloudflare's own message (cut to 300 chars, token scrubbed), the HTTP status and `Retry-After` on `429`; transient = network failure, `429`, `5xx`. | Implemented | `TestListZonesPaginatesAndOrders`, `TestListRecordsMergesTypesAndOrders`, `TestGetAndUpdateRecord`, `TestCloudflareErrors`, `TestClientRefusesPathTraversalInIDs`, `TestNewCloudflareValidatesTheURL`, `TestEmptyTokenIsRefusedLocally` |
| REQ-DDNS-003 | **Configuration.** A DDNS configuration has `name`, `zone_id`, `record_id`, `record_name`, `record_type` (`A`/`AAAA`), `proxied`, `ttl` (1 = automatic, otherwise up to 86400; a proxied record is always automatic), `interval_seconds` (60..86400, default 300), `enabled`. Invalid input is `400`. One Cloudflare record is managed by at most one configuration (`400`, the spec has no `409` here). The Controller keys are `controller.ddns.ip_providers`, `cloudflare_api_url` and `allow_insecure_http` (REQ-RT-013). | Implemented | `TestCreateValidation`, `TestCreateNormalisesProxiedTTLAndPaddedToken`, `TestCreateDuplicates`, `TestCreateDdnsConfigValidationOverHTTP`, `TestDDNSConfig` |
| REQ-DDNS-004 | **Create, token and record id.** `POST /ddns` (`201`) requires `record_id`: the record is the one the user chose from the lookup, **never resolved by name**. The `api_token` is trimmed, sealed with the master key (AAD `ddns_configs.api_token`) and stored only as a BLOB; responses carry `has_api_token` and never the token; it appears in no log line, error, audit entry or activity item. On create the record is read from Cloudflare with that token and must exist, be of the configured type and name (else `400 bad_request` with Cloudflare's reason); the check needs no write permission. | Implemented | `TestCreateSealsTheTokenAndStoresTheRecordID`, `TestCreateVerifiesTheRecordWithCloudflare`, `TestRepositoryRoundTripAndConstraints`, `TestDDNSLifecycleOverHTTP`, `TestCreateDdnsConfigValidationOverHTTP`; smoke test 2026-11-14 (token absent from log, DB, audit) |
| REQ-DDNS-005 | **Update and delete.** `PATCH /ddns/{id}` is partial. Changing `zone_id`, `record_name` or `record_type` **requires `record_id` in the same request** (`400`). A new token or a changed target is verified with Cloudflare first (`400` if rejected); a changed target clears the observed state (`last_ip`, `detected_ip`, `dns_value`, errors). A write that raced with a sync discards the sync's result. `DELETE` removes the configuration and its history (`204`; `404` when unknown). Unknown id on `PATCH`, `DELETE`, `sync` is `404`. | Implemented | `TestUpdateRules`, `TestProxiedForcesAutomaticTTLOnUpdate`, `TestDeleteCascadesHistory`, `TestSyncResultIsDroppedWhenTheConfigChangedMeanwhile`, `TestDDNSLifecycleOverHTTP` |
| REQ-DDNS-006 | **Sync.** One code path serves the scheduler and `POST /ddns/{id}/sync` and is serialised per configuration: discover the public address (REQ-DDNS-001), read the record by id, check it still has the configured type and name (else the sync fails with `permanent` and **never writes** to it), then `PATCH` only when `content`, `proxied` or `ttl` differ. Each attempt stores `detected_ip`, `dns_value`, `last_checked_at`, `last_ip`/`last_synced_at` (success) or `last_error`/`last_error_at`, and one `ddns_sync_history` row (`updated`, `unchanged`, `failed`). The manual endpoint answers `200` with `result` (`updated`/`unchanged`/`failed`), `ip`, `error` and `synced_at`: a failed sync is a **result**, not an HTTP error. | Implemented | `TestSyncUpdatesThenReportsUnchanged`, `TestSyncDetectsDriftAtCloudflare`, `TestSyncProxiedAndTTLAreDesiredState`, `TestSyncAAAAUsesTheIPv6Address`, `TestSyncNeverUpdatesTheWrongRecord`, `TestSyncFailures`, `TestSyncCancelledRecordsNothing`, `TestSyncsOfOneConfigAreSerialised`, `TestDDNSLifecycleOverHTTP` |
| REQ-DDNS-007 | **Syncer job** (`Syncer.Run(ctx)`, one per Controller). A 5 s tick finds due configurations; each enabled one runs on its own `interval_seconds`, after a restart immediately, after an edit at once, never after a delete. Transient failures retry with exponential backoff 1 s, 2 s, 4 s ... capped at 5 min and at the configuration's interval, jittered to 50..100 %; Cloudflare's `Retry-After` is honoured; permanent failures (bad token, record mismatch) wait for the normal interval; success resets the backoff. One configuration's failures or slowness never delay another (each sync has its own goroutine, 4 at once). Cancelling the context stops the job, waits for running syncs and leaks nothing; a panic in one sync is contained. | Implemented | `TestSyncerRunsEachConfigOnItsInterval`, `TestSyncerBacksOffOnTransientFailures`, `TestSyncerBackoffIsJitteredAndNeverLongerThanTheInterval`, `TestSyncerConfigsAreIndependent`, `TestSyncerSlowConfigDoesNotBlockOthers`, `TestSyncerConcurrencyIsBounded`, `TestSyncerHonoursRateLimits`, `TestSyncerPermanentFailuresWaitForTheNextInterval`, `TestSyncerEditsApplyImmediatelyAndDeletesAreForgotten`, `TestSyncerRunStopsAndLeaksNothing`, `TestSyncerShutdownWhileSyncing`, `TestSyncerSurvivesAPanic`, `TestBackoffDelay`, `TestIsTransient`; smoke test 2026-11-14 (backoff 5 s, 5 s, 5 s, 5 s, 5 s, 15 s observed) |
| REQ-DDNS-008 | **Audit and activity.** `ddns.create`, `ddns.update`, `ddns.delete` (actor = the user) and `ddns.sync` (a manual sync, any result; a **scheduled** sync only when it changed the record, actor `system`) are written to `audit_log` and appear in the activity feed under category `ddns` with English messages. The audit details hold only name, record name, IP, result, trigger and the **names** of changed fields (a failed manual sync also keeps the sync error text, which never contains the token or a provider URL); the feed exposes only the whitelisted keys (REQ-API-023). Never the token, a provider URL or a Cloudflare payload. A scheduled run that finds nothing to do is not audited (a log line at debug level only). | Implemented | `TestDDNSActivityFeed`, `TestSyncerAuditsUpdatesOnly`, `activity.TestMessages`, `activity.TestFeedExposesOnlyWhitelistedData` |

## Cloudflare lookups (REQ-API-020)

`POST /ddns/cloudflare/zones` and `POST /ddns/cloudflare/zones/{zone_id}/records` feed the form's
dropdowns. The body holds exactly one of `api_token` (a token being entered) or `config_id` (use the
stored token); neither or both is `400`, an unknown `config_id` is `404`. They store nothing, return
zones or `A`/`AAAA` records ordered by name, and map every Cloudflare failure to `502 cloudflare_error`
with Cloudflare's reason. Verified by `TestCloudflareLookupsOverHTTP`, `TestCloudflareLookupFailuresAre502`,
`TestDDNSAndMetricsRequireAuthentication`, `TestLookups`.

## System metrics

`GET /api/v1/system/metrics` (any authenticated user, REQ-API-025) returns a snapshot of the host
that runs the Controller.

| ID | Requirement | Status | Verified by |
|----|-------------|--------|-------------|
| REQ-SYS-001 | **Collection.** On Linux and macOS (Windows compiles but is untested; its load average is restricted) the `Gopsutil` provider (`github.com/shirou/gopsutil/v4`, ADR-016) fills: hostname, platform (`GOOS/GOARCH`), kernel, host uptime, CPU utilisation over the last sampling window and core count, load average (1/5/15 min), memory (total, available, used), disk usage of the file system that holds the data directory, non-loopback local IPs, and process pid, uptime, RSS, goroutines and heap. Every metric is either present or named in `restricted`; nothing is silently zero. | Implemented | `TestGopsutilSnapshotHasEveryFieldOrRestrictsIt`, `TestBusyPercent`, `TestLocalIPsArePublicOrPrivateUnicastOnly`, `TestGopsutilFirstCollectionHonoursCancellation` |
| REQ-SYS-002 | **Fallback.** `RuntimeProvider` (Go runtime only: platform, hostname, cores, goroutines, heap, process uptime, local IPs) is the base of `Gopsutil` and the whole provider where gopsutil cannot run. What it cannot know (CPU %, memory, disk, load, kernel, host uptime, RSS) is listed in `restricted`, e.g. `["cpu_percent","memory","disk"]`. `restricted` is always present in the response, possibly empty. A gopsutil failure of one metric restricts that metric and does not fail the call. | Implemented | `TestRuntimeProviderRestrictsWhatItCannotKnow`, `TestGopsutilSnapshotHasEveryFieldOrRestrictsIt` |
| REQ-SYS-003 | **Cheap polling.** The provider is wrapped in `Cached` (TTL 3 s): at most one collection per TTL however often the endpoint is polled, concurrent callers share it, errors are not cached. The CPU reading is the **delta between two samples** (the first call waits up to ~750 ms to have two; later calls never block); until there are two it is absent and not in `restricted`, not a made-up `0`. | Implemented | `TestCachedServesOneSnapshotPerTTL`, `TestBusyPercent`, `TestGopsutilSnapshotHasEveryFieldOrRestrictsIt` |
| REQ-SYS-004 | **Endpoint.** The response conforms to `SystemMetrics` in the spec (bytes as integers, `collected_at`, optional `cpu_percent`, `restricted`); `401` without a token; no secrets and no paths other than the data-directory disk path. ## Known gaps

- **No real Cloudflare account and no real public-IP providers** were used: the Cloudflare client was
  built from the documented v4 envelope and tested against `ddnstest` and a throwaway fake. Rate-limit
  and error codes of the live service are as documented, not observed. First live run is an owner action.
- The configured **IP providers learn the Controller's public address** by design; they cannot be
  avoided when asking "what is my IP". The default list and a replacement list are in
  `configs/homecore.example.yaml`.
- The syncer's tick is 5 s, so a retry scheduled 1 s ahead runs at the next tick; backoff steps shorter
  than the tick are rounded up to it.
- A legacy row with an empty `cf_record_id` (none can exist: no writer existed before Phase 4) would
  need a `record_id` on its first `PATCH`.
- Outcomes are kept in `ddns_sync_history` (retention, REQ-RET-001) but there is no endpoint that lists
  them; the activity feed and `last_*` fields are the UI's view.
- CPU percentage precision on macOS is coarse (OS counters); the first value after start can take
  ~750 ms.
- DDNS tokens cannot be rotated in place other than by `PATCH` with a new `api_token`; there is no
  multi-record-per-config or wildcard support (one configuration, one record).
