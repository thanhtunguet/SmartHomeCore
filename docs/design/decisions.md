# Architecture Decision Records

These answer the five open questions from `BRIEF.md` §8 plus the foundational choices. Format:
context → decision → consequences. Status of all records: **Accepted (v0.2)** unless noted.

---

## ADR-001 — Agent command authentication: Ed25519 signatures

**Context.** The Controller must prove to an Agent that a command is authentic, fresh and intended
for that Agent. Options: static secret (rejected by the brief), HMAC-SHA256 with a per-agent shared
secret, Ed25519 signatures.

**Decision.** Ed25519. The Controller owns a signing key pair (private key sealed in its DB). Each
Agent is configured with the **public keys** of the Controllers it trusts (`agent.trusted_controllers`).
Replay protection is mandatory and independent of the signature scheme: timestamp window, nonce
cache, process-start floor and `command_id` idempotency (see [agent-protocol.md](agent-protocol.md)).

**Consequences.**
- A compromised Agent host leaks nothing that can forge commands to other Agents.
- Provisioning is copy-paste of one public key (`GET /api/v1/system/controller-key`, or
  `devtools keygen` during development) into the Agent config; no secret distribution.
- Multiple Controllers are natural (ADR-005).
- Content is authenticated, not encrypted. Confidentiality needs TLS (agent supports optional TLS)
  or a VPN. Commands contain no secrets, so this is acceptable on a home LAN.
- HMAC remains a fallback only if Ed25519 is ever unavailable on a target (it is in Go stdlib, so not
  expected).

## ADR-002 — Device identity

**Context.** DHCP may change IPs; hostnames may be unresolvable; MACs change when a NIC changes.

**Decision.** A device is identified by a server-generated **UUID** (v7). `ip_address`, `hostname` and
`mac_address` are mutable attributes. A device may be bound to an Agent identified by its own
`agent_id` (UUID generated by the Agent on first start and persisted in its data dir). The probe
target is `hostname` when set, otherwise `ip_address`. The command payload carries the target
`agent_id`, and the Agent rejects commands addressed to another `agent_id` — so a stale IP that now
belongs to a different Agent can never execute someone else's shutdown.

**Consequences.** IP changes need a manual edit in MVP. Later: Agent announces itself (signed) so the
Controller can update the IP automatically.

## ADR-003 — Command state machine

**Decision.** `pending → sent → acknowledged → completed | failed | timed_out`, with `wake` skipping
`acknowledged`. Completion is verified **only** by the monitor (online for wake, offline for
shutdown) before a deadline. HTTP endpoints return `202` with the command immediately. A second
request for the same device and type while one is active returns the active command.

**Consequences.** The UI shows honest progress. The brief's `unknown` outcome is called `timed_out` to
avoid a name clash with device status.

## ADR-004 — SQLite driver: `modernc.org/sqlite` everywhere

**Context.** We need one storage implementation for Linux, macOS, Windows and Android (gomobile).
Options: `mattn/go-sqlite3` (cgo, needs C toolchain per target incl. NDK), `modernc.org/sqlite`
(pure Go, transpiled C), `ncruces/go-sqlite3` (Wasm via wazero), or a Kotlin-side storage adapter.

**Decision.** `modernc.org/sqlite` behind `internal/storage`, no Android-specific storage adapter.

**Evidence.** `CGO_ENABLED=0 go build` with the driver succeeds for `android/arm64`, `linux/arm64`,
`linux/arm`, `linux/amd64`, `windows/amd64`, `darwin/arm64`. `android/arm` (32-bit) cannot link
without cgo — a Go toolchain constraint for Android executables, not a driver issue; gomobile always
builds with cgo + NDK, so it is expected to work but **must be verified in the Phase 0 spike**.

**Consequences.** Trivial cross-compilation; larger binary (~+6 MB) and somewhat slower than cgo
SQLite, irrelevant at this load. If the spike fails on a target, fall back to `ncruces/go-sqlite3`
(same `database/sql` interface) without touching domain code.

## ADR-005 — Multiple Controllers

**Decision.**
- Each Controller has its own key pair and `key_id`. An Agent lists all Controllers it trusts.
- Monitoring and WOL from several Controllers are allowed (idempotent, harmless).
- Commands carry a globally unique `command_id`; the Agent executes a given `command_id` at most once
  and, after accepting a power action, ignores further power actions during a cooldown
  (default 60 s), answering `already_scheduled`.
- No leader election or Controller-to-Controller sync in MVP. Each Controller keeps its own DB.

**Consequences.** Two Controllers can show slightly different histories; that is accepted.

## ADR-006 — Spec-first REST API

**Decision.** `api/openapi.yaml` (OpenAPI 3.0.3) is the source of truth. `oapi-codegen` (pinned as a
Go `tool` dependency) generates models, a chi `ServerInterface` and the embedded spec into
`internal/api/gen`. Generated code is committed; CI checks it is up to date (`make generate && git
diff --exit-code`). Handlers embed `gen.Unimplemented` so documented-but-unbuilt operations return 501.

**Consequences.** Docs cannot drift from routes or request/response shapes. Contributors (and AI
agents) change the YAML first, then regenerate, then implement.

---

## ADR-007 — Modular monolith, minimal layering

**Decision.** One Go module, packages per capability under `internal/`. Consumer-side interfaces,
constructor injection in `internal/app`, no DI framework, no global state. Layers (model / service /
repository) are added per package only when justified.

## ADR-008 — Offline Swagger UI

**Decision.** Pinned `swagger-ui-dist` assets are committed under `web/swagger/` (fetched once by
`scripts/fetch-swagger-ui.sh`) and embedded with `//go:embed`. The page loads `/api/openapi.json`
from the same origin. No CDN at runtime.

## ADR-009 — Frontend integrated into the repository and embedded into the binary

**Context.** The web UI (HomeCoreUI: React 19, Vite 8, Tailwind 4) lives in its own repository. The
Controller must serve it without a separate web server (brief §3.1, MVP "static file serving"), and
`go build` must keep working with `CGO_ENABLED=0` for all seven targets without Node.

**Decision.**
- The UI source is tracked directly in `frontend/` in the HomeCore repository; its former standalone
  repository history is retained through a subtree import. `make ui-build` builds it into
  `web/static/`, which `//go:embed all:static` ships in the binary. `web/static/*` is git-ignored
  except `.gitkeep`, so the embed directive is valid on a fresh checkout.
- If `web/static/index.html` is absent, `web.Static()` serves `web/placeholder/index.html` instead.
- `make build` / `make cross` do not need Node. `make build-full` builds the UI first; release
  builds must use it.
- The UI calls same-origin relative URLs only. In development, Vite proxies `/api`, `/healthz` and
  `/readyz` to a local Controller, so CORS stays off.
- The UI conforms to the Controller's CSP: bundled fonts, no inline scripts, no `data:` assets.
- Wire types in the UI are hand-written from `api/openapi.yaml` (the generator needs TypeScript 5,
  the UI uses 7). This is a known drift risk (GAP-INF-06).

**Consequences.** Frontend and backend source live in one repository and are built from the same
checkout. The GitHub Actions workflow no longer fetches a submodule; UI changes are committed with
the rest of HomeCore. The historical subtree import may be updated from the former upstream only
through an explicit subtree pull.

## ADR-010 — UI session tokens in localStorage and polling instead of push

**Context.** The API returns JWT access and rotating refresh tokens in JSON bodies (no cookie flow).
The scope guardrails exclude WebSocket/SSE.

**Decision.**
- The UI keeps the session (access token, refresh token, expiry, user) in `localStorage`, shared
  across tabs. A refresh happens before expiry and once on `401`, serialised with the Web Locks API
  where the browser offers it (secure contexts only).
- Live data is polled (devices 10 s, commands 15 s, metrics 10 s, DDNS 30 s, health 60 s), paused in
  hidden tabs.
- Long operations (wake, shutdown) are followed by polling `GET /commands/{id}`; the API answers
  `202` and never blocks.

**Consequences.** Tokens are readable by any script running on the origin, so the strict CSP is
the main mitigation; acceptable for a home LAN, to be revisited before exposing the Controller to
the Internet (httpOnly cookie flow). Without a secure context (plain `http://` on the LAN) the
multi-tab refresh race is only narrowed, so the Controller should tolerate a short reuse grace window
when it implements refresh rotation (GAP-INF-01). Polling cost grows with open tabs; fine at the
target scale (< 10 users).

## ADR-011 — No roles: every authenticated user is equal

**Context.** The brief (§3.1, §6) and the first design had two roles, `admin` and `viewer`, with
shutdown, device management and DDNS reserved to `admin`. The system is a small household
installation; the people who can log in already trust each other and the maintainers asked for
no permission model (2026-11-14).

**Decision.** Authentication stays mandatory, authorization by role is removed.
- Any authenticated user may call every `/api/v1` operation. The spec has no scopes on `bearerAuth`;
  `middleware.PolicyFromSpec` aborts startup if one reappears, so nothing is silently granted.
- `users` has no `role` column (migration `0003`); `auth.Principal` has no role; the `403 Forbidden`
  response and the `Role` schema are gone. A route without a policy entry is still denied (`403`, fail closed).
- Shutdown still writes `audit_log`, with the acting user.
- Accounts are managed outside the API: `homecore user add|passwd` (Phase 1b). There is no
  first-run bootstrap with a default or logged password, and no user-management API or UI.

**Consequences.** Any account can shut a machine down and change DDNS records (the Cloudflare token
stays write-only). Supersedes brief §6.1 ("roles") and §6.7 ("shutdown requires admin"). Revisit
together with ADR-010 if the Controller is ever exposed beyond the LAN or shared with people who
should not operate devices.

## ADR-012 — Idempotent, fail-fast power commands with a per-device throttle

**Context.** On a LAN a wake or shutdown is answered in milliseconds. The earlier design left open
what to do when a device is already in the target state or a command is already running (`409`?),
used a 5 s timeout with three retries for the agent request, and had no protection against button
mashing.

**Decision.**
- **Idempotent.** Sending the same command again behaves like sending it once and is never an
  error. An active command of the same type is returned (`202`); a device already `online` (wake) or
  `offline` (shutdown) gets a command that completes at once, without a packet or an agent request.
  A wake and a shutdown for one device are independent (the unique index is per `(device_id, type)`).
- **Fail fast.** `409` remains only for a request that can never work (wake without a MAC, shutdown
  without an agent binding). A dispatch problem is reported as `failed` immediately: one attempt to
  the agent with a short timeout (2 s) and at most one immediate retry with the same `command_id`.
  The long `deadline_at` (wake 180 s, shutdown 120 s) is unchanged; it bounds how long the *machine*
  takes to boot or stop, not the LAN round trip.
- **Throttle.** At most one wake/shutdown request per device per second, counted over all users and
  both types. Excess requests get `429 rate_limited` with `Retry-After`. It is enforced by the
  backend (`middleware.DeviceThrottle`, after authentication, in memory) and again by the UI, which
  does not send the request and disables that device's buttons for the second.

**Consequences.** Clients need no special handling for "already done". The throttle state is lost on
restart, which is acceptable. A refresh of the agent-protocol retry policy
([agent-protocol §5](agent-protocol.md#5-controller-behaviour)) follows from this ADR.

## ADR-013 — Authentication implementation: argon2id, stdlib HS256 JWT, refresh grace window

**Context.** Phase 1b needs password storage, access/refresh tokens and a way to create the first
account (ADR-011 removed the bootstrap). The Controller runs on small devices (Raspberry Pi,
Android TV boxes), the UI cannot serialise refreshes across tabs on plain HTTP (ADR-010,
GAP-INF-01), and dependencies must stay few (AGENTS.md).

**Decision.**
- **Passwords: argon2id** via `golang.org/x/crypto/argon2` (the only new dependency; approved). Cost
  `m=32 MiB, t=3, p=1`: above the OWASP minimum for argon2id, about a quarter to half a second on a
  Pi 4, at most two hashes at once (64 MiB peak). The PHC string carries the parameters; hashes are
  upgraded at the next login. Rejected: bcrypt (72-byte limit, not memory-hard), scrypt (no standard
  encoded form in the stdlib ecosystem we use).
- **JWT without a library.** HS256 with `crypto/hmac`; about 150 lines including strict header
  pinning (exactly `alg=HS256`, no extra header members) so `alg=none` and algorithm confusion
  cannot occur. Single issuer and verifier, one symmetric key, no `kid`, no key sets, so a general
  library would only add attack surface. The key is random, sealed in `system_settings`, distinct
  from the master key and the Controller Ed25519 key.
- **Revocation of access tokens by lookup, not by versioning.** Each request reads the user row, so a
  disabled or deleted account is rejected immediately. Token versions or a `jti` deny-list would
  add state for little gain at < 10 users. Consequence accepted: logout and password change do not
  cut off an access token before `exp` (≤ 15 min); they revoke refresh tokens.
- **Refresh tokens: opaque, SHA-256 at rest, rotation with family reuse detection, plus a 10 s
  grace window.** Inside the window a replayed (already rotated) token returns the pair that was
  issued for it, instead of revoking the family. To return it without keeping a plaintext refresh
  token, the pair is stored sealed (AES-GCM, master key) on the used row (`successor_sealed`,
  migration `0004`) and wiped when the window ends. Rejected: re-minting a different successor
  (would fork the family and break reuse detection), a longer window (widens theft exposure), and
  storing the refresh token in plaintext or as a reversible value without sealing.
- **Login: one verification for every outcome** (dummy hash for unknown users), identical generic
  `401`, reason only in `audit_log`; the submitted username is audited only if it names an account.
- **First account: `homecore user add|passwd|list`** working on the DB file; password from
  `HOMECORE_PASSWORD`, stdin, or a no-echo prompt. No-echo uses `golang.org/x/sys` (termios, Windows
  console mode) in `internal/platform/tty` because `golang.org/x/term` is not an approved
  dependency; `golang.org/x/sys` moved from an indirect to a direct dependency (already in `go.mod`).
  Minimum password length 12 (`auth.MinPasswordLength`).

**Consequences.** `go.mod` gains `golang.org/x/crypto` (and `go mod` raised the indirect
`golang.org/x/text`). The 10 s window lets a thief who replays a just-rotated token obtain the same
pair as the legitimate client; reuse after the window is still detected. The grace window is a
constant, not a config key. The JWT key cannot be rotated without signing everybody out.
Supersedes the "JWT" and "login hygiene" lines of the earlier design notes only in detail, not in
direction (ADR-010, ADR-011 stand).

## ADR-014 — Phase 2 decisions: manual probes feed hysteresis, client-side "wake many", urgent probing

**Context.** Phase 2 left three questions open: whether `POST /devices/{id}/probe` should change the
stored state, how to offer "wake many" (brief §3.4), and how a wake gets verified quickly without
the commands engine and the monitor depending on each other.

**Decision.**
- **A manual probe is a real observation.** It goes through the same hysteresis tracker, updates
  `status`, `last_checked_at`, `last_seen_at` and `last_latency_ms`, may append a history row
  (reason `manual probe`) and notifies the commands engine. The response returns both the raw
  result (`reachable`) and the status after hysteresis. Rejected: a probe that only reports and
  stores nothing (the API would show `offline` while the list still says `online`, and a wake would
  not complete from it), and a probe that bypasses hysteresis (one failed manual probe would flip
  a healthy device to `offline`).
- **"Wake many" is client-side fan-out.** The UI calls `wakeDevice` for each selected device. No
  batch endpoint: wake is idempotent and per-device throttled (ADR-012), the 202 + `Command`
  contract is per device, a batch would need its own partial-failure and throttle semantics, and
  with a home-sized fleet the extra requests cost nothing. Revisit only if a client needs a single
  atomic acknowledgement. The spec is unchanged.
- **Urgent probing instead of an engine → monitor call.** The monitor selects "enabled devices plus
  devices with an active command" from the database and probes the latter on every tick. The
  commands engine therefore never calls the monitor to schedule a re-check, and the monitor never
  imports the engine: it only knows a small `Observer` interface it defines, and `internal/app`
  connects the two (`SetObserver`). The cost is one extra query per tick, which also gives restart
  recovery for free (an active command after a restart makes its device urgent again).
- **The monitor's tracker is seeded from the stored status** (not `unknown`) after a restart, so a
  restart does not erase the status or write spurious history. Failure counters stay in memory.
- **A stored `online` is confirmed before a wake becomes a no-op.** The engine asks the monitor for
  one fresh probe, so a stale status cannot silently swallow a wake request.

**Consequences.** A manual probe by any user affects the stored status; that is intended. A device
with an active command is probed every tick (5 s by default) regardless of its interval. A client
that wants an atomic "wake these N" must handle N responses. No new dependency (the conformance
test uses `github.com/getkin/kin-openapi`, already a direct dependency for the spec-derived
authorization policy; its `openapi3filter` and `routers/legacy` packages need no new module).

## ADR-015 — Phase 3 decisions: agent status semantics, health job and the activity feed

**Context.** Phase 3 connected the Controller to the Agent. Four things the earlier ADRs left open:
what `agent.status` means, how it is kept fresh, what the Controller trusts in an Agent's answer,
and how the UI gets a feed of "what happened" without a second event store.

**Decision.**
- **`agent.status` is what the Controller last learned, not a live probe.** `ready` = the *bound*
  agent answered (a protocol 4xx other than `wrong_agent` counts: the Agent is alive and refusing
  on purpose). `unreachable` = network error, 5xx, an answer that is not a HomeCore agent, a
  different `agent_id` than the binding's, or the host is known offline. `unknown` = never
  contacted, or the binding's `agent_id`, port or scheme changed (the three fields reset).
  `last_ok_at` moves only on success. Stored in `agent_bindings` (migration `0005`), never derived
  on read, so list endpoints stay one query.
- **Two writers, one rule.** The shutdown Dispatcher records every attempt; a health job
  (`agentctl.Health`, once a minute, concurrency 4, not a config key) calls
  `GET /agent/v1/healthz` for bound devices that are `online` and checks that the returned
  `agent_id` is the bound one, because a reused IP or a cloned machine must not look `ready`.
  Both write through `RecordAgentContact`, a compare-and-set on the binding's `agent_id`, so a
  result that arrives after a re-bind is dropped. Offline devices are not probed: an agent that was
  `ready` becomes `unreachable` without a request.
- **The Controller trusts an Agent answer only if the body names the bound `agent_id` and
  `command_id`.** Anything else is `agent_bad_response`. The HTTP client takes no proxy, follows no
  redirects and keeps no connections, so a command cannot be bounced to another host.
- **Retry stays at one immediate repeat** (ADR-012, agent-protocol §5), with the same `command_id`
  and a fresh nonce. A 4xx is never retried.
- **The activity feed is a view of `audit_log`, not a new table.** `GET /api/v1/activity` pages
  `audit_log` newest first with a keyset cursor `{t, i}`, derives `category` from the action prefix
  (`auth`, `device`, `command`, `ddns`, `user`, `system`), joins `devices` for names and exposes only a
  whitelist of `details` keys, so a future audit detail cannot leak through the API by accident.
  Rejected: a separate events table (two stores to keep consistent) and returning `details` verbatim.
- **Audit write is best effort for shutdown.** `device.shutdown` is written after the dispatch;
  a failed write is logged, not returned. The earlier architecture note suggested refusing the action
  when the audit row cannot be written. The same database has already accepted the command row just
  before, so a failure there is rare and refusing afterwards would not undo the dispatch; refusing
  before would need a write-ahead record. Left as an open owner decision.

**Consequences.** After a machine boots, `agent.status` can lag by up to one health interval (60 s);
while a device is offline and the agent was `ready`, the next pass corrects it. The feed shows only
what is audited: probes and monitor transitions are not in it. Changing the interval or making it
configurable is a code change, not a config key, until a need appears. No new dependency, no wire
change, protocol stays v1.

## ADR-016 — Phase 4 decisions: public-IP quorum, record ids, DDNS state and metrics

**Context.** Phase 4 made the Controller change DNS records on its own and report on its host. A
wrong public address written to DNS breaks remote access, and a sync that updates the wrong record
can break something unrelated, so the rules below favour doing nothing over guessing. gopsutil was
approved as the one new module for metrics (`golang.org/x/crypto` came with Phase 1b).

**Decision.**
- **Quorum, not majority.** The public IP is accepted only if **at least 2 providers return the same
  address and no other address has as many answers** (`ddns.decide`). Two providers must exist, on
  different hosts, over `https` (config check). The answer must be a bare address of the requested
  family and **public**: loopback, private, link-local, CGNAT, documentation, multicast, 6to4, NAT64,
  Teredo and similar ranges are refused (a Controller behind a proxy or captive portal must not
  publish `10.x`). Sockets are pinned to the family (`tcp4`/`tcp6`), so an `A` record never learns an
  IPv6 address. Redirects are followed only to the same host (an open redirect cannot move the
  question to an unlisted third party), no proxy is used (it would answer with the proxy's address),
  bodies are 128 bytes at most. One success is shared and cached 10 s per family. Provider URLs can
  carry keys, so only the host appears in errors and logs. Rejected: first-answer-wins, strict
  majority of all providers (one provider being down must not stop DDNS), and a single provider with
  a fallback.
- **A configuration points at a record id, never at a name.** `record_id` is required on create;
  `PATCH` that changes the zone, name or type must carry a `record_id` too (`400` otherwise); the
  sync reads the record by id and **refuses to write** if its type or name differ from the
  configuration. A partial unique index on `(zone_id, cf_record_id)` stops two configurations from
  managing one record. The spec has no `409` for DDNS, so duplicates and a record that does not match
  are `400 bad_request` with a specific message. Create and a token or target change verify the record
  with Cloudflare (read-only call) so a typo fails at the form, not at 3 am.
- **Observed state is stored separately from pushed state.** Migration `0006` adds `detected_ip`
  (what discovery saw), `dns_value` (what Cloudflare held) and `last_checked_at`, next to `last_ip`
  (what the Controller last wrote or confirmed), so the UI can show drift and "checked but unchanged".
  A sync result is saved only if the configuration was not edited meanwhile (compare-and-set on
  `updated_at`); history is written in the same transaction.
- **One sync path.** The scheduler and the manual endpoint call `Service.Sync`, serialised per
  configuration. A failed sync is a value (`DdnsSyncResult.result = failed`), not an HTTP error: the
  request itself succeeded. Lookups are the exception and are `502 cloudflare_error` because there the
  call to Cloudflare *is* the request.
- **Failures are classified.** Transient (network, `429`, `5xx`, quorum failure) back off 1 s → 5 min,
  jittered, capped at the interval, `Retry-After` honoured. Permanent (bad token, record mismatch)
  wait for the next interval instead of hammering Cloudflare. Each configuration has its own
  schedule; a slow or failing one cannot delay another (own goroutine, 4 at once). The schedule is
  in memory: after a restart every enabled configuration is due at once (cheap, and a restart is when
  an address may have changed).
- **Audit is not a log of polling.** Scheduled syncs are audited only when they changed the record;
  manual syncs always. Everything else is a log line.
- **No Cloudflare SDK.** Four endpoints over `net/http` with a typed error (status, Cloudflare code,
  scrubbed message, `Retry-After`) are smaller than a dependency and keep the token handling visible.
- **Metrics: gopsutil on top of the runtime provider.** `system.Gopsutil` extends
  `system.RuntimeProvider`; anything it cannot read is named in `restricted` (always present in the
  response) instead of being reported as `0`. CPU % is a delta between samples and absent until two
  exist. `system.Cached` (3 s) bounds the cost of polling. gopsutil v4 is pure Go and keeps
  `CGO_ENABLED=0` and `make cross` green (checked for the seven targets).

**Consequences.** DDNS can fail to update while a provider is down and another disagrees: that is
the intended price of never trusting one source. The providers learn the Controller's public IP (to be
stated in the example config). A bad answer from Cloudflare cannot make the Controller write to a
record it did not choose. The first metrics call can take up to ~750 ms. A new dependency
(`github.com/shirou/gopsutil/v4`, plus its small transitive set) was approved with the Phase 4 brief.
Not decided: rotation of provider lists at runtime (needs a restart), multi-record configurations and
wildcard records.

## ADR-017 — Legacy device endpoints and long-lived, scoped client tokens

**Context.** Apps written for the single-device predecessor call three plain `GET`s:
`/api/turn-on`, `/api/turn-off` and `/api/is-online` (the last answers the text `true` or `false`).
The Controller now manages many devices, so each call must say which one. The old apps cannot do
a login and refresh cycle, but they already send a fixed `Authorization: Bearer <string>` header
(2026-11-14), so the endpoints can stay authenticated instead of being opened to the LAN.

**Decision.**
- **Three spec operations** `legacyTurnOn`, `legacyTurnOff`, `legacyIsOnline` at `GET /api/turn-on`,
  `/api/turn-off`, `/api/is-online`, tagged `legacy`, security `bearerAuth` (not public). The device is
  the required query parameter `device`: a UUID is an id, anything else a name (case-insensitive).
  Ids issued here are UUIDv7 (never integers), so in practice the name is used; a numeric value is a
  name. The UI builds the URL with the name unless the id is an integer.
- **Adapters, not a second implementation.** Turn-on/off call the same `commands.Engine` requests as
  wake and shutdown (same idempotency, same `409`s, same audit `device.wake`/`device.shutdown`, with
  `via: legacy` in the details) and share the one-per-device-per-second throttle (ADR-012), applied
  after the device is resolved so a name and an id of one device share a slot. Success is `200`
  with the text `true` (old apps expect a plain success, not `202` plus JSON); every failure uses the
  usual JSON envelope and status.
- **Long-lived scoped tokens.** `homecore token create --user NAME [--label] [--ttl 10y]` signs an
  ordinary HS256 access token for an existing account with a `scp: "legacy"` claim and a long
  lifetime (default 10 years, at most 20). `middleware.Authorize` refuses a scoped token with `403`
  on every operation that is not tagged `legacy` in the spec, so a leaked client token can do
  nothing beyond what the old app could already do. The token is printed once and never stored;
  the audit entry `auth.legacy_token_issue` records user, label, token id and expiry only.
- **Revocation** is the account's: the token is checked against the `users` row on every request,
  so disabling or deleting the account kills it; replacing the JWT signing key kills all tokens.
  There is no per-token revocation list (no new table); one account per client gives per-client
  revocation. `user passwd` does not revoke access tokens (REQ-AUTH known gap).

**Consequences.** A leaked token can wake and shut down every device until it expires or its account
is disabled; a `GET` that powers a machine off is also exposed to link prefetchers and to proxies
that log URLs (the token is in a header, not the URL, which is why it is not a query parameter).
Disabling an account still needs SQL until `homecore user disable` exists (backlog). Not decided:
a revocation list, per-token labels in a table, restricting a token to chosen devices.

## ADR-018 — Service account keys: server-generated Ed25519 keys, scoped, individually revocable and self-rotating

*Partly superseded by [ADR-020](#adr-020--the-controller-hosts-the-mcp-server-the-service-account-key-is-the-only-credential): the Controller hosts the MCP server and accepts any key on it.*

**Context.** The legacy endpoints (ADR-017) and AI agents (an MCP server calling the Controller) need
credentials that outlive a login session, that a user can create with a chosen lifetime, and that
can be cut off one by one. The HS256 legacy tokens cannot: they have no row, so revoking one means
disabling its account or replacing the signing key for everybody. An agent must also be able to renew
its own credential without a human.

**Decision.**
- **A key is a row in `service_account_keys`** (migration `0007`): owner (`users.id`), name, scope,
  TTL, `expires_at`, and the key material. Created by `POST /service-account-keys` with a **session**
  token; `ttl_seconds` defaults to one year (60 s to 20 years). Actions made with a key are attributed
  to the owning user (ADR-011: no roles, so no separate "service account" principal).
- **The Controller generates an Ed25519 key pair per key and keeps the private key in the database,
  sealed** with the master key (AES-GCM, AAD `service_account_keys.private_key:<id>`, REQ-SEC-006). It
  is independent of the JWT signing key, the master key and the Controller's agent-signing key.
- **The credential is a JWT** (`alg: EdDSA`, `kid` = key id, claims `sub`, `iat`, `exp`, `jti`, `scp`)
  signed with that private key, sent as `Authorization: Bearer <key>`. It is shown once, in the
  response that created it, and never stored. Because Ed25519 signatures are deterministic and the
  claims are a function of the row, the Controller can rebuild the very same credential from the row
  when it must (see rotation). `auth.Router` sends EdDSA tokens to `servicekey.Service` and HS256
  tokens to the session authenticator.
- **Verification** (every request): strict header (`alg` EdDSA, `typ` JWT or absent, `kid` required,
  nothing else), `kid` lookup, signature with the stored public key, then the **row** decides: not
  revoked, not past `expires_at`, not past its rotation grace; claims `sub`/`scp`/`jti` equal the
  row; the owner exists and is not disabled. Revoking, disabling the owner or deleting it therefore
  works at once. `last_used_at` is refreshed at most once a minute.
- **Scopes.** `legacy` (the three legacy operations) and `mcp` (device control and read-only
  monitoring). Which operations accept a scope is written in the spec: the operation-level extension
  `x-token-scopes: [...]` (the `legacy` tag still implies the scope `legacy`). `middleware.Authorize`
  answers `403` when a key's scope is not listed, so a new operation is **session-only until someone
  lists it**. The `mcp` allowlist is: `getCurrentUser`, `listDevices`, `getDevice`, `getDeviceHistory`,
  `probeDevice`, `wakeDevice`, `shutdownDevice`, `listCommands`, `getCommand`, `getSystemInfo`,
  `getSystemMetrics`, `listActivity`, the legacy operations, and rotation. It excludes device and DDNS
  configuration, the Controller key, key management and logout. Create, list and revoke carry no
  `x-token-scopes`: a key can never mint or revoke keys.
- **Rotation: `POST /auth/service-key/rotate`**, authenticated by the key being replaced. The
  Controller checks it is valid (not revoked, not expired), creates a new key (new key pair) with the
  same owner, name and scope and the old key's TTL (or the request's `ttl_seconds`), and returns it.
  The old key is **superseded, not revoked**: it works for `RotationGrace` (1 minute) and then dies.
  A repeat of the call with the old key inside that window returns the **same** successor (rebuilt
  from its sealed private key) instead of creating a second one, so a client that lost the response
  cannot be locked out; after the window the old key is `401`, and if the successor was meanwhile
  revoked, rotated again or is gone, the answer is `409`. The path is under `/auth/`, so it gets the
  per-IP limit of the login endpoints. Only a key can call it (a session token gets `403`).
- **Audit:** `service_key.create`, `service_key.revoke`, `service_key.rotate` (details: ids, name,
  scope, expiry, `replayed`, `via_key_id`; never the credential), written in the same transaction as
  the change. Device audit entries made with a key carry `service_key_id`.
- **Retention:** `service_account_keys` is a `retention` target: rows that expired, were revoked or
  were superseded longer than `retention_days` ago are deleted.

**Alternatives considered.** *Opaque random secrets stored hashed* (like refresh tokens): simpler
and the server would keep nothing derivable, but the brief for this feature asked for server-held
private keys, and the derivable credential is what makes the rotation retry idempotent without a
second sealed column. *Keys held by the client that sign short-lived assertions*: no bearer secret
on the wire, but the legacy apps cannot sign anything and an MCP client would need custom code.

**Consequences.** The credential is a **bearer secret**: whoever has it acts as the owner within its
scope until it expires or is revoked; there is no proof of possession and no per-device or per-IP
restriction. Anyone who has the database and the master key can mint valid credentials for any key
row, exactly as they could already forge session tokens with the JWT key. During the grace window a
stolen old key can fetch the new key (the price of retry safety; the window is a constant). The
legacy HS256 tokens of ADR-017 remain and are still revoked only through their account; new
integrations should use keys. The MCP server itself is **not part of this repository**: the `mcp`
scope is the contract it authenticates against. Not decided: per-key device restrictions, a
user-facing "rotate this key" by id, a cap on keys per user, UI screens (frontend submodule).

## ADR-019 — Portable Agent: identity and trusted key as arguments, setup prompt

**Context.** The Agent created its own `agent_id` in a data directory on first start (ADR-002). The
operator then had to read the id from the log or the file and type it into the Controller, write a
config file with the Controller public key, and on Windows set `data_dir` by hand because the default
`./data` is relative to the working directory (`System32` when elevated). The Agent is meant to run on
small, disposable machines, so it should need no file on the system.

**Decision.** Supersedes only the clause of ADR-002 that says the Agent generates its id and persists it
in its data dir; the Controller-side identity model and the `wrong_agent` check are unchanged.
- **The Controller side chooses the id.** The web UI makes a UUIDv7 in the browser (device form,
  Remote Shutdown tab) and saves it in the binding; it also builds the **command** that starts the Agent
  for Windows, Linux and macOS:
  `homecore --mode agent --agent-id <uuid> --trusted-controller <public key> --agent-listen :<port>`
  (`.\homecore.exe` on Windows). No API change: the binding already carries `agent_id`, and the key is
  `GET /system/controller-key`.
- **The Agent accepts them as arguments**: `--agent-id` (env `HOMECORE_AGENT_ID`, config `agent.id`),
  `--trusted-controller` (repeatable, added to `agent.trusted_controllers`), `--agent-listen` (env
  `HOMECORE_AGENT_LISTEN`). With an id given, nothing is read from or written to the data dir. Without
  one, the id persisted in `<agent.data_dir>/agent_id` is used and created if missing, as before, so existing
  installs and non-interactive starts do not change.
- **Setup prompt.** In `--mode agent` (not `both`), on a terminal, with no id from flag, environment,
  config or `agent_id` file, the binary asks for the command copied from the UI instead of starting. It
  parses it (`internal/agentsetup`), writes the service files for the OS in the working directory and
  prints the install steps, then exits without starting or installing anything. Linux:
  `homecore-agent.service` (id and key in `ExecStart`, same hardening as `deploy/systemd`, no state
  directory) and the polkit rule. Windows: `HomeCore Agent.lnk` created through PowerShell
  (`WScript.Shell`) with "Run as administrator" set, plus printed `Register-ScheduledTask` and
  `New-NetFirewallRule` lines. Other systems: the command is printed.
- **The pasted text is data.** It is split into words and only `--mode agent`, `--agent-id`,
  `--trusted-controller` and `--agent-listen` are accepted; each value is validated (UUID, a parseable
  Ed25519 key, `host:port` with a restricted host alphabet) and the files are rendered from the
  validated values. Existing, different files are never overwritten.

**Alternatives considered.** *Config file generated by the UI*: another file to move, and the
trust anchor would still live on disk. *Agent registers itself with the Controller (enrolment)*: needs
an unauthenticated or token-protected inbound endpoint on the Controller and a new protocol; out of
MVP scope. *A `.lnk` generated by the Controller*: a binary format and the elevation flag make it
fragile; the Agent creates it on the machine where it will run.

**Consequences.**
- The id and the Controller **public** key are in the unit file, the shortcut and the process list. Neither is a secret
  (signatures authenticate commands, agent-protocol §3); there is still no secret on the Agent.
- Two Agents given the same id would both accept a command signed for it. The id exists to stop a
  command reaching the wrong machine after an IP change (ADR-002), so each machine needs its own; the
  Controller already refuses to bind one id to two devices, and the operator is responsible for not
  copying a command between machines.
- Rotating the Controller key or changing the id means regenerating the service file or shortcut.
- The generated polkit rule is a Go constant kept equal to `deploy/polkit/50-homecore-agent.rules` by a test.
- The Windows shortcut, the Linux unit and the `.lnk` elevation flag have **not** been run on real
  hosts (no Windows machine; no systemd host in this session).
- Not decided: macOS launchd generation, TLS flags for the Agent (an `https` binding still needs `agent.tls` in a config file), a Windows Service wrapper.

## ADR-020 — The Controller hosts the MCP server; the service account key is the only credential

**Context.** AI agents (Claude and others) should be able to list the home's machines and turn them on
and off. ADR-018 assumed an MCP server in a separate project that calls the REST API with an `mcp`-scoped
key. The decision now is that the backend serves MCP itself, authenticated by a service account key, with
**no permission layer of its own**: any valid key may use every tool, and if permissions are ever needed
they belong to the key (a future scope or a per-key setting), not to the tools.

**Decision.**
- **One endpoint, `POST /api/v1/mcp`**, in the OpenAPI spec like every other operation (operation
  `callMcp`, tag `mcp`). It speaks MCP over **stateless Streamable HTTP without SSE**: each `POST` carries one
  JSON-RPC 2.0 message and a request is answered `200 application/json`; notifications and client responses are
  `202` with no body; `GET` and `DELETE` are `405`; batches are refused (`400`). There are no sessions
  (`Mcp-Session-Id` is not issued) and the server never pushes. This stays inside the guardrail against
  WebSocket/SSE.
- **Hand-written protocol layer, `internal/mcp`, standard library only.** It implements `initialize` (version
  negotiation among `2025-11-25`, `2025-06-18`, `2025-03-26`), `ping`, `tools/list` and `tools/call`. No MCP SDK
  is added: the surface is four methods, and a dependency would need to be justified against the "no new heavy
  dependencies" rule. The package knows nothing about devices or authentication.
- **Authentication = the existing key.** `middleware.Authorize` authenticates the bearer exactly as for every
  operation; the operation lists `x-token-scopes: [legacy, mcp]`, i.e. **every key scope is accepted**. The
  handler additionally requires that the principal is a **key** (`Principal.KeyID != ""`), so a session or
  legacy HS256 token is `403`. No other check: no allowlist, no per-tool rule.
- **Three tools**, adapters over the same services as REST and the legacy endpoints (so the same throttle,
  idempotency and audit apply):
  - `list_devices`: every device (pages of 100, at most 500) in a compact view: id, name, description, type, OS,
    enabled, `status`, `power_transition`, `last_seen_at`, `last_checked_at`, `can_turn_on` (has a MAC address),
    `can_turn_off` (has an agent). MAC, IP, ports and the agent binding are left out.
  - `get_devices`: one device, by `device` = id or name (`devices.Service.Resolve`, ADR-017). The name is
    plural as requested although it returns one device.
  - `control_device` with `device` and `action`: `turn_on` = wake (`requestWake`), `turn_off` = signed shutdown
    (`requestShutdown`), `check_status` = `Monitor.ProbeNow` now, then the stored device. `turn_on`/`turn_off`
    take the per-device slot of REST/legacy (ADR-012) and return the command (`202` semantics, never waiting
    for the machine); the audit entry says `via: mcp` and carries `service_key_id`, the actor is the key's owner.
- **Errors the model can fix are tool results with `isError: true`** (unknown device, unknown action, no MAC,
  no agent, throttled), with a hint in the text; only malformed JSON-RPC, unknown methods and unknown tools
  are protocol errors. Internal failures are logged and reported as "internal error", never with detail.
- Results carry the JSON as text **and** as `structuredContent`; tool annotations say which tools are
  read-only and that `control_device` is destructive but idempotent.

**Alternatives considered.** *A separate MCP server process or project* (ADR-018's assumption): one more thing to
deploy and to keep in step with the API, and it would have to hold the key itself. *The official Go SDK*:
saves little code and adds a dependency. *Full Streamable HTTP with SSE and sessions*: needed only for
server-initiated messages, which this server never sends. *Exposing the REST API as tools one to one*: far more
surface for an agent than "list, get, switch".

**Consequences.** Any valid key, whatever its scope, can power machines on and off through MCP; the
`legacy` scope no longer confines a key to the three legacy URLs. A leaked key is as strong as its owner
for these tools until it expires or is revoked (ADR-018). The `mcp` scope of ADR-018 and its REST allowlist
still exist and are untouched; they are redundant for MCP and can be removed later (that needs a migration,
because `service_account_keys.scope` has a CHECK on it). The endpoint does not validate the `Origin` header
(DNS rebinding): it needs a bearer key, which a browser page cannot attach. No resumability and no
server-to-client notifications. The superseded clause of ADR-018 is "the MCP server itself is **not part of this
repository**".

## ADR-021 — Alerts: channels, adapters and hooks in the producers

**Context.** The owner wants to be told, on Telegram first and on other channels later, about: a new public
IP (DDNS), a wake or shutdown request, and a machine that changes state outside HomeCore's control (seen online,
then silent, or the reverse). Alerts are not in the brief and not in the MVP list of the scope guardrails;
they are added at the owner's request. They must not weaken any security invariant, slow the monitor or the
request path, or pull in a dependency.

**Decision.**
- **A new package, `internal/alerts`, with channels stored in the database.** A channel is a row of
  `alert_channels` (migration `0008`): name, `type` (the adapter), `enabled`, `events`, flat string `settings`,
  and **one** sealed `secret`. Channels are managed through the REST API (`/alerts/channels`, spec-first, session
  token only), like DDNS configurations, not through the YAML file: the owner adds a Telegram target from the
  UI, a token in a file would be plaintext, and the DDNS precedent already has the sealing and the audit.
- **Adapters are a `Factory(settings, secret) (Adapter, error)` registered by `internal/app`**, where the factory
  is also the validation. `Adapter` is one method, `Send(ctx, Message{Kind, Title, Body})`. The first adapter,
  Telegram, takes exactly the two asked parameters: `secret` = bot token, `settings.target_user_id` = the
  target. It talks to the Bot API `sendMessage` with the standard library (no SDK, no new dependency), plain
  text only (no `parse_mode`, so a device name cannot break the message). One secret plus flat string
  settings is enough for the adapters one can foresee (Discord/Slack webhook: the URL is the secret; email:
  the password is the secret); an adapter that needs more would need an ADR.
- **Hooks are observer interfaces owned by the producers and implemented in `internal/alerts`**:
  `ddns.IPObserver` (in `Service.Sync`, so scheduler and manual sync alike), `commands.IssueObserver` (in
  `Engine.Request`, so REST, legacy and MCP alike) and `monitoring.TransitionObserver`. The producers do not
  import `alerts`; `app` wires. This keeps the dependency direction of the guardrails and puts each hook where
  the fact is known exactly once.
- **Three events** a channel can subscribe to (default: all): `ip_changed`, `power_command`, `status_changed`.
- **"Out of control" is decided by the active command.** A status transition is reported unless a command that
  explains it is in progress (wake explains `online`, shutdown explains `offline`). The monitor calls the
  transition hook **before** the commands engine (the Observer) completes the command, which is the one
  ordering this relies on. First sightings (`unknown`) and disabled devices are not reported. We reuse the
  monitor's hysteresis instead of adding a second debounce.
- **Delivery is asynchronous and best effort.** `Notify` queues (64 entries, in memory) and returns; one
  `Run(ctx)` consumer delivers in order, to the channels in parallel, with up to three attempts (1 s, 5 s) on
  temporary failures (network, `429`, `5xx`), and stores the outcome on the channel (`last_sent_at`,
  `last_error`). A full queue drops the new alert; a stop loses the queue.
- **The secret never leaves.** Sealed with AAD `alert_channels.secret`, write-only in the API (`has_secret`),
  out of the audit log and the logs. The Bot API puts the token in the URL, so the Telegram adapter removes the
  URL from transport errors and scrubs the token from the replies it quotes.
- **Audit** `alert_channel.create|update|delete|test` with the acting user and field names only; the alerts
  themselves are not audited.

**Alternatives considered.** *Channels in the YAML config*: plaintext token, restart to change, no UI path. *A
telegram-specific table and endpoint*: the next adapter would repeat it. *Alert from the audit log* (poll
`audit_log` for `device.wake`, `ddns.sync`): misses the monitor's transitions, delivers late, and ties alerts to
what happens to be audited. *A persistent outbox with replay*: an alert about the moment loses its value when
replayed later, and it adds a table and a job for a home-sized system. *A message broker*: excluded by the
guardrails and unnecessary for one consumer. *Parsing markup (MarkdownV2/HTML)*: escaping rules make a device
named `NAS_1` a delivery error.

**Consequences.** One more table and one more `errgroup` member. The three producers each gained an optional
observer and still work without one. Alerts are lost across a Controller restart and during a Telegram outage
longer than the retries; a Controller that is down cannot alert about itself. A device that bounces produces a
message per change (no flap suppression beyond hysteresis). Messages are English. The frontend has no
screen yet and its generated types are stale until regenerated. A live run against Telegram has not been done.

## ADR-022 — Port forwarding: a userspace relay driven by stored rules

**Context.** The owner wants the Controller to forward ports: pick the local interface to listen on (default
`0.0.0.0`), the connection type (TCP, UDP or "Universal" = both), give each rule a name, and switch each rule on
and off, with the on/off state remembered so that a restart brings the enabled rules back. Port forwarding is not
in the brief and not in the MVP list of the scope guardrails; it is added at the owner's request. It opens
listening sockets on the host, so it must not weaken a security invariant, and it must run on every target the
Controller runs on (Linux, macOS, Windows, Android), without CGO and without a new dependency.

**Decision.**
- **A relay inside the Controller process, in the standard library** (`internal/portforward`, `net` only). For
  TCP: accept, dial the target, copy both ways with half-close. For UDP: one upstream socket per client address
  so replies return to the right client, forgotten after 60 s of silence. A rule is the pair of sockets plus the
  goroutines that serve them; stopping a rule closes the sockets and every relayed connection and waits for the
  goroutines.
- **Rules are rows of `port_forward_rules`** (migration `0009`) managed through the REST API (`/port-forwards`,
  spec-first, session token only), like DDNS configurations and alert channels. `enabled` is the **desired**
  state and is the only runtime-related column; whether a listener is open now is held in memory and reported as
  `status`.
- **Restart is a reconcile, not a replay.** `Service.Run` lists the rules and starts the enabled ones, then every
  15 s starts any enabled rule that is not listening. A bind failure (port in use, interface not up at boot, no
  privilege) is a rule state (`error` plus the reason), never a Controller failure, and is retried: after a boot
  where the network comes up late, the rules come up by themselves. Nothing listens before `Run` is called.
- **`protocol` is `tcp`, `udp` or `universal`** (the owner's word for both). A `universal` rule binds TCP and UDP
  on the same port number and relays each to the target port; it is all-or-nothing.
- **The listen address is an IP literal, validated for syntax only.** It is not checked against the host's
  interfaces on save, so a rule for an address that is down at boot can still be saved and is retried; the UI
  fills the choice from `local_addresses` of the metrics endpoint (no new endpoint). IPv4 literals bind with the
  `tcp4`/`udp4` networks so `0.0.0.0` stays IPv4, as written.
- **Overlap and loop checks in the service**, under the same lock that starts the rule: two enabled rules cannot
  take the same socket, and a rule cannot forward a port to itself. A disabled rule reserves nothing.
- **Limits per rule** (512 TCP connections, 256 UDP clients, 5 s connect timeout, 64 KiB datagrams) so a flood or
  a dead target cannot exhaust file descriptors or memory on a small host.
- **Session only.** The operations have no `x-token-scopes`, so a service account key (`legacy`, `mcp`) gets `403`:
  an AI agent or a legacy client cannot open a port. Audit `port_forward.create|update|enable|disable|delete`
  with the acting user.

**Security consequences (accepted, recorded).**
- A rule makes the Controller host a relay: anyone who can reach the listen port reaches the target, with the
  Controller's network position. There is no source allow-list and no authentication on the relayed port. The
  default `0.0.0.0` exposes it on every interface, as asked.
- A rule may target loopback or any address the Controller can reach, so it can expose a service that listens only
  on the host. That is the point of the feature, and it is why the operations are session-only. Because there are
  no roles (ADR-011), every signed-in user can do it; for a household of fewer than ten trusted users this is the
  same trust as shutting machines down.
- The packaged systemd unit has `CapabilityBoundingSet=` empty, so ports below 1024 fail with "permission denied"
  (shown as the rule's error). We do **not** widen the unit for everyone; `deploy/README.md` gives an opt-in
  drop-in with `CAP_NET_BIND_SERVICE`.

**Alternatives considered.** *Drive `iptables`/`nftables`/`pf`*: needs root and a different implementation per OS,
cannot run on Android, and the Controller runs unprivileged by design. *`socat` or another external process*: a
dependency to install, supervise and keep in sync with the database. *Store `status` in the database*: it would be
stale after a crash and forces a write on every retry; the desired state is the only fact worth storing.
*Check the listen address against the interfaces on save*: rejects a rule for an interface that is down at boot,
which is exactly when persistence matters. *Refuse loopback targets*: forbids the common use (publish a local-only
service on a LAN port) and would not stop a determined user. *A role for port forwarding*: ADR-011.

**Consequences.** One more table and one more `errgroup` member. A TCP rule is a user-space copy, so it is slower
than kernel forwarding and the target sees the Controller's address, not the client's (no PROXY protocol). Changing
a rule's listener or target drops its connections. Established connections do not survive a Controller restart.
Rules are not verified on Linux, Android or with IPv6 sockets yet (REQ-PF known gaps).
