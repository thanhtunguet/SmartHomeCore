# Architecture Decision Records

These answer the five open questions from `BRIEF.md` §8 plus the foundational choices. Format:
context → decision → consequences. Status of all records: **Accepted (v0.2)** unless noted.

---

## ADR-001 — Agent command authentication: Ed25519 signatures

**Context.** The Controller must prove to an Agent that a command is authentic, fresh and intended
for that Agent. Options: static secret (rejected by the brief), HMAC-SHA256 with a per-agent shared
secret, Ed25519 signatures.

**Decision.** Ed25519. The Controller owns a signing key pair (private key sealed in its DB). Each
Agent is configured with the **public keys** of the Controllers it trusts (`agent.trusted_controllers`).
Replay protection is mandatory and independent of the signature scheme: timestamp window, nonce
cache, process-start floor and `command_id` idempotency (see [agent-protocol.md](agent-protocol.md)).

**Consequences.**
- A compromised Agent host leaks nothing that can forge commands to other Agents.
- Provisioning is copy-paste of one public key (`GET /api/v1/system/controller-key`, or
  `devtools keygen` during development) into the Agent config; no secret distribution.
- Multiple Controllers are natural (ADR-005).
- Content is authenticated, not encrypted. Confidentiality needs TLS (agent supports optional TLS)
  or a VPN. Commands contain no secrets, so this is acceptable on a home LAN.
- HMAC remains a fallback only if Ed25519 is ever unavailable on a target (it is in Go stdlib, so not
  expected).

## ADR-002 — Device identity

**Context.** DHCP may change IPs; hostnames may be unresolvable; MACs change when a NIC changes.

**Decision.** A device is identified by a server-generated **UUID** (v7). `ip_address`, `hostname` and
`mac_address` are mutable attributes. A device may be bound to an Agent identified by its own
`agent_id` (UUID generated by the Agent on first start and persisted in its data dir). The probe
target is `hostname` when set, otherwise `ip_address`. The command payload carries the target
`agent_id`, and the Agent rejects commands addressed to another `agent_id` — so a stale IP that now
belongs to a different Agent can never execute someone else's shutdown.

**Consequences.** IP changes need a manual edit in MVP. Later: Agent announces itself (signed) so the
Controller can update the IP automatically.

## ADR-003 — Command state machine

**Decision.** `pending → sent → acknowledged → completed | failed | timed_out`, with `wake` skipping
`acknowledged`. Completion is verified **only** by the monitor (online for wake, offline for
shutdown) before a deadline. HTTP endpoints return `202` with the command immediately. A second
request for the same device and type while one is active returns the active command.

**Consequences.** The UI shows honest progress. The brief's `unknown` outcome is called `timed_out` to
avoid a name clash with device status.

## ADR-004 — SQLite driver: `modernc.org/sqlite` everywhere

**Context.** We need one storage implementation for Linux, macOS, Windows and Android (gomobile).
Options: `mattn/go-sqlite3` (cgo, needs C toolchain per target incl. NDK), `modernc.org/sqlite`
(pure Go, transpiled C), `ncruces/go-sqlite3` (Wasm via wazero), or a Kotlin-side storage adapter.

**Decision.** `modernc.org/sqlite` behind `internal/storage`, no Android-specific storage adapter.

**Evidence.** `CGO_ENABLED=0 go build` with the driver succeeds for `android/arm64`, `linux/arm64`,
`linux/arm`, `linux/amd64`, `windows/amd64`, `darwin/arm64`. `android/arm` (32-bit) cannot link
without cgo — a Go toolchain constraint for Android executables, not a driver issue; gomobile always
builds with cgo + NDK, so it is expected to work but **must be verified in the Phase 0 spike**.

**Consequences.** Trivial cross-compilation; larger binary (~+6 MB) and somewhat slower than cgo
SQLite, irrelevant at this load. If the spike fails on a target, fall back to `ncruces/go-sqlite3`
(same `database/sql` interface) without touching domain code.

## ADR-005 — Multiple Controllers

**Decision.**
- Each Controller has its own key pair and `key_id`. An Agent lists all Controllers it trusts.
- Monitoring and WOL from several Controllers are allowed (idempotent, harmless).
- Commands carry a globally unique `command_id`; the Agent executes a given `command_id` at most once
  and, after accepting a power action, ignores further power actions during a cooldown
  (default 60 s), answering `already_scheduled`.
- No leader election or Controller-to-Controller sync in MVP. Each Controller keeps its own DB.

**Consequences.** Two Controllers can show slightly different histories; that is accepted.

## ADR-006 — Spec-first REST API

**Decision.** `api/openapi.yaml` (OpenAPI 3.0.3) is the source of truth. `oapi-codegen` (pinned as a
Go `tool` dependency) generates models, a chi `ServerInterface` and the embedded spec into
`internal/api/gen`. Generated code is committed; CI checks it is up to date (`make generate && git
diff --exit-code`). Handlers embed `gen.Unimplemented` so documented-but-unbuilt operations return 501.

**Consequences.** Docs cannot drift from routes or request/response shapes. Contributors (and AI
agents) change the YAML first, then regenerate, then implement.

---

## ADR-007 — Modular monolith, minimal layering

**Decision.** One Go module, packages per capability under `internal/`. Consumer-side interfaces,
constructor injection in `internal/app`, no DI framework, no global state. Layers (model / service /
repository) are added per package only when justified.

## ADR-008 — Offline Swagger UI

**Decision.** Pinned `swagger-ui-dist` assets are committed under `web/swagger/` (fetched once by
`scripts/fetch-swagger-ui.sh`) and embedded with `//go:embed`. The page loads `/api/openapi.json`
from the same origin. No CDN at runtime.

## ADR-009 — Frontend as a git submodule, embedded into the binary

**Context.** The web UI (HomeCoreUI: React 19, Vite 8, Tailwind 4) lives in its own repository. The
Controller must serve it without a separate web server (brief §3.1, MVP "static file serving"), and
`go build` must keep working with `CGO_ENABLED=0` for all seven targets without Node.

**Decision.**
- The UI is the git submodule `frontend/`. `make ui-build` builds it into `web/static/`, which
  `//go:embed all:static` ships in the binary. `web/static/*` is git-ignored except `.gitkeep`, so
  the embed directive is valid on a fresh checkout.
- If `web/static/index.html` is absent, `web.Static()` serves `web/placeholder/index.html` instead.
- `make build` / `make cross` do not need Node. `make build-full` builds the UI first; release
  builds must use it.
- The UI calls same-origin relative URLs only. In development, Vite proxies `/api`, `/healthz` and
  `/readyz` to a local Controller, so CORS stays off.
- The UI conforms to the Controller's CSP: bundled fonts, no inline scripts, no `data:` assets.
- Wire types in the UI are hand-written from `api/openapi.yaml` (the generator needs TypeScript 5,
  the UI uses 7). This is a known drift risk (GAP-INF-06).

**Consequences.** Frontend and backend release independently but are pinned together by the
submodule pointer. UI changes must be committed in the submodule first, then the pointer updated.
The submodule URL is SSH; CI needs a key or an HTTPS URL.

## ADR-010 — UI session tokens in localStorage and polling instead of push

**Context.** The API returns JWT access and rotating refresh tokens in JSON bodies (no cookie flow).
The scope guardrails exclude WebSocket/SSE.

**Decision.**
- The UI keeps the session (access token, refresh token, expiry, user) in `localStorage`, shared
  across tabs. A refresh happens before expiry and once on `401`, serialised with the Web Locks API
  where the browser offers it (secure contexts only).
- Live data is polled (devices 10 s, commands 15 s, metrics 10 s, DDNS 30 s, health 60 s), paused in
  hidden tabs.
- Long operations (wake, shutdown) are followed by polling `GET /commands/{id}`; the API answers
  `202` and never blocks.

**Consequences.** Tokens are readable by any script running on the origin, so the strict CSP is
the main mitigation; acceptable for a home LAN, to be revisited before exposing the Controller to
the Internet (httpOnly cookie flow). Without a secure context (plain `http://` on the LAN) the
multi-tab refresh race is only narrowed, so the Controller should tolerate a short reuse grace window
when it implements refresh rotation (GAP-INF-01). Polling cost grows with open tabs; fine at the
target scale (< 10 users).

## ADR-011 — No roles: every authenticated user is equal

**Context.** The brief (§3.1, §6) and the first design had two roles, `admin` and `viewer`, with
shutdown, device management and DDNS reserved to `admin`. The system is a small household
installation; the people who can log in already trust each other and the maintainers asked for
no permission model (2026-11-14).

**Decision.** Authentication stays mandatory, authorization by role is removed.
- Any authenticated user may call every `/api/v1` operation. The spec has no scopes on `bearerAuth`;
  `middleware.PolicyFromSpec` aborts startup if one reappears, so nothing is silently granted.
- `users` has no `role` column (migration `0003`); `auth.Principal` has no role; the `403 Forbidden`
  response and the `Role` schema are gone. A route without a policy entry is still denied (`403`, fail closed).
- Shutdown still writes `audit_log`, with the acting user.
- Accounts are managed outside the API: `homecore user add|passwd` (Phase 1b). There is no
  first-run bootstrap with a default or logged password, and no user-management API or UI.

**Consequences.** Any account can shut a machine down and change DDNS records (the Cloudflare token
stays write-only). Supersedes brief §6.1 ("roles") and §6.7 ("shutdown requires admin"). Revisit
together with ADR-010 if the Controller is ever exposed beyond the LAN or shared with people who
should not operate devices.

## ADR-012 — Idempotent, fail-fast power commands with a per-device throttle

**Context.** On a LAN a wake or shutdown is answered in milliseconds. The earlier design left open
what to do when a device is already in the target state or a command is already running (`409`?),
used a 5 s timeout with three retries for the agent request, and had no protection against button
mashing.

**Decision.**
- **Idempotent.** Sending the same command again behaves like sending it once and is never an
  error. An active command of the same type is returned (`202`); a device already `online` (wake) or
  `offline` (shutdown) gets a command that completes at once, without a packet or an agent request.
  A wake and a shutdown for one device are independent (the unique index is per `(device_id, type)`).
- **Fail fast.** `409` remains only for a request that can never work (wake without a MAC, shutdown
  without an agent binding). A dispatch problem is reported as `failed` immediately: one attempt to
  the agent with a short timeout (2 s) and at most one immediate retry with the same `command_id`.
  The long `deadline_at` (wake 180 s, shutdown 120 s) is unchanged; it bounds how long the *machine*
  takes to boot or stop, not the LAN round trip.
- **Throttle.** At most one wake/shutdown request per device per second, counted over all users and
  both types. Excess requests get `429 rate_limited` with `Retry-After`. It is enforced by the
  backend (`middleware.DeviceThrottle`, after authentication, in memory) and again by the UI, which
  does not send the request and disables that device's buttons for the second.

**Consequences.** Clients need no special handling for "already done". The throttle state is lost on
restart, which is acceptable. A refresh of the agent-protocol retry policy
([agent-protocol §5](agent-protocol.md#5-controller-behaviour)) follows from this ADR.

## ADR-013 — Authentication implementation: argon2id, stdlib HS256 JWT, refresh grace window

**Context.** Phase 1b needs password storage, access/refresh tokens and a way to create the first
account (ADR-011 removed the bootstrap). The Controller runs on small devices (Raspberry Pi,
Android TV boxes), the UI cannot serialise refreshes across tabs on plain HTTP (ADR-010,
GAP-INF-01), and dependencies must stay few (AGENTS.md).

**Decision.**
- **Passwords: argon2id** via `golang.org/x/crypto/argon2` (the only new dependency; approved). Cost
  `m=32 MiB, t=3, p=1`: above the OWASP minimum for argon2id, about a quarter to half a second on a
  Pi 4, at most two hashes at once (64 MiB peak). The PHC string carries the parameters; hashes are
  upgraded at the next login. Rejected: bcrypt (72-byte limit, not memory-hard), scrypt (no standard
  encoded form in the stdlib ecosystem we use).
- **JWT without a library.** HS256 with `crypto/hmac`; about 150 lines including strict header
  pinning (exactly `alg=HS256`, no extra header members) so `alg=none` and algorithm confusion
  cannot occur. Single issuer and verifier, one symmetric key, no `kid`, no key sets, so a general
  library would only add attack surface. The key is random, sealed in `system_settings`, distinct
  from the master key and the Controller Ed25519 key.
- **Revocation of access tokens by lookup, not by versioning.** Each request reads the user row, so a
  disabled or deleted account is rejected immediately. Token versions or a `jti` deny-list would
  add state for little gain at < 10 users. Consequence accepted: logout and password change do not
  cut off an access token before `exp` (≤ 15 min); they revoke refresh tokens.
- **Refresh tokens: opaque, SHA-256 at rest, rotation with family reuse detection, plus a 10 s
  grace window.** Inside the window a replayed (already rotated) token returns the pair that was
  issued for it, instead of revoking the family. To return it without keeping a plaintext refresh
  token, the pair is stored sealed (AES-GCM, master key) on the used row (`successor_sealed`,
  migration `0004`) and wiped when the window ends. Rejected: re-minting a different successor
  (would fork the family and break reuse detection), a longer window (widens theft exposure), and
  storing the refresh token in plaintext or as a reversible value without sealing.
- **Login: one verification for every outcome** (dummy hash for unknown users), identical generic
  `401`, reason only in `audit_log`; the submitted username is audited only if it names an account.
- **First account: `homecore user add|passwd|list`** working on the DB file; password from
  `HOMECORE_PASSWORD`, stdin, or a no-echo prompt. No-echo uses `golang.org/x/sys` (termios, Windows
  console mode) in `internal/platform/tty` because `golang.org/x/term` is not an approved
  dependency; `golang.org/x/sys` moved from an indirect to a direct dependency (already in `go.mod`).
  Minimum password length 12 (`auth.MinPasswordLength`).

**Consequences.** `go.mod` gains `golang.org/x/crypto` (and `go mod` raised the indirect
`golang.org/x/text`). The 10 s window lets a thief who replays a just-rotated token obtain the same
pair as the legitimate client; reuse after the window is still detected. The grace window is a
constant, not a config key. The JWT key cannot be rotated without signing everybody out.
Supersedes the "JWT" and "login hygiene" lines of the earlier design notes only in detail, not in
direction (ADR-010, ADR-011 stand).

## ADR-014 — Phase 2 decisions: manual probes feed hysteresis, client-side "wake many", urgent probing

**Context.** Phase 2 left three questions open: whether `POST /devices/{id}/probe` should change the
stored state, how to offer "wake many" (brief §3.4), and how a wake gets verified quickly without
the commands engine and the monitor depending on each other.

**Decision.**
- **A manual probe is a real observation.** It goes through the same hysteresis tracker, updates
  `status`, `last_checked_at`, `last_seen_at` and `last_latency_ms`, may append a history row
  (reason `manual probe`) and notifies the commands engine. The response returns both the raw
  result (`reachable`) and the status after hysteresis. Rejected: a probe that only reports and
  stores nothing (the API would show `offline` while the list still says `online`, and a wake would
  not complete from it), and a probe that bypasses hysteresis (one failed manual probe would flip
  a healthy device to `offline`).
- **"Wake many" is client-side fan-out.** The UI calls `wakeDevice` for each selected device. No
  batch endpoint: wake is idempotent and per-device throttled (ADR-012), the 202 + `Command`
  contract is per device, a batch would need its own partial-failure and throttle semantics, and
  with a home-sized fleet the extra requests cost nothing. Revisit only if a client needs a single
  atomic acknowledgement. The spec is unchanged.
- **Urgent probing instead of an engine → monitor call.** The monitor selects "enabled devices plus
  devices with an active command" from the database and probes the latter on every tick. The
  commands engine therefore never calls the monitor to schedule a re-check, and the monitor never
  imports the engine: it only knows a small `Observer` interface it defines, and `internal/app`
  connects the two (`SetObserver`). The cost is one extra query per tick, which also gives restart
  recovery for free (an active command after a restart makes its device urgent again).
- **The monitor's tracker is seeded from the stored status** (not `unknown`) after a restart, so a
  restart does not erase the status or write spurious history. Failure counters stay in memory.
- **A stored `online` is confirmed before a wake becomes a no-op.** The engine asks the monitor for
  one fresh probe, so a stale status cannot silently swallow a wake request.

**Consequences.** A manual probe by any user affects the stored status; that is intended. A device
with an active command is probed every tick (5 s by default) regardless of its interval. A client
that wants an atomic "wake these N" must handle N responses. No new dependency (the conformance
test uses `github.com/getkin/kin-openapi`, already a direct dependency for the spec-derived
authorization policy; its `openapi3filter` and `routers/legacy` packages need no new module).
